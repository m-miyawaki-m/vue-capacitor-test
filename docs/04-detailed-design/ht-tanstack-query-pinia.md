# TanStack Query と Pinia の使い分け

## 現行 PoC の判断

**現行の在庫検索 PoC は Pinia のレスポンス Store で十分と判断し、TanStack Query は見送る。** 商品コードを指定する検索 API が1本で、検索ボタンを押すたびに最新結果を取得する運用を想定する。複数の独立した API の結果について、鮮度と再取得を並行して管理する要件はない。結果の表示、取得中・失敗の状態、同じ条件での再取得失敗時に前回結果を保持する処理は、既存の Store 設計で扱える。

複数の取得結果の鮮度や再取得を管理する要件が生じた場合は、TanStack Query を再検討する。たとえば、入庫確定後に複数の一覧・詳細を再取得する場合や、一覧と詳細を頻繁に往復し、前回結果を表示しながら最新データを取り直す場合が該当する。

現行の AC3 には条件別の結果保持が含まれる。直近の結果だけに簡略化する場合は、業務上の必要性を確認し、受入基準の変更として扱う。

## 再検討時の構成案

再検討条件に該当した段階で、TanStack Vue Query の採用を判断する。人間が採用と受入条件の変更を判断し、Codex が結果を方針に記録する。

採用時は API の成功本文・取得状態・エラーを Query キャッシュに一本化し、Pinia への複製や同期を設けない。移行後の業務では対応するレスポンス Store を廃止し、Pinia は確定条件などの画面制御を担当する。

| 状態・処理 | 採用時の担当 | 在庫検索での例 |
| --- | --- | --- |
| 画面だけで使う入力 | Vue のローカル状態 | 入力中の商品コード。入力のたびには検索しない。 |
| 画面間で保持・復元する状態 | Pinia の画面制御 Store | 確定済みの検索条件、パネル開閉、一覧のスクロール位置。 |
| サーバー由来の状態 | TanStack Query のキャッシュ | 条件ごとの一覧、ID ごとの詳細、取得状態、エラー、更新時刻。 |
| HTTP と契約検証 | Orval の生成 Fetch クライアントと手書きの API 境界 | HTTP ステータスを判定し、Zod 検証済み本文を返す。失敗は種類付きの `ApiError` とする。 |
| 入庫登録後の再取得 | Query の mutation 成功処理 | 影響する在庫一覧・詳細のキーを無効化する。更新 API と影響範囲は後続で決める。 |

## 在庫検索に当てはめた場合

1. 検索ボタンで商品コードを正規化して確定する。空白のみの入力ではリクエストを発行しない。別の条件を入力中は、最後に確定した条件の一覧を表示する。
2. 一覧のキーは `['inventory', 'list', { productCode }]`、詳細専用 API が必要な場合のキーは `['inventory', 'detail', id]` を候補とする。倉庫・ページ・並び順など、リクエストの結果を変える条件が増えたらキーに含める。Vue のリアクティブな確定条件をキーに結び付け、取得にも同じ条件を使う。
3. Query の取得関数から既存の API 境界を呼ぶ。画面は同じキーの `data` とエラー状態を読み、再取得に失敗したら前回の成功データとエラーを同時に表示する。別条件へ切り替えた際は、新しいキーに属する結果だけを表示する。
4. 一覧データだけで詳細表示を満たせる場合は、一覧キーと項目 ID からキャッシュ内の1件を参照する。新しい URL から直接開いた場合やキャッシュが消えた場合の復元、詳細専用 API の要否と一意 ID は後続で決める。倉庫や利用者によって取得結果が変わる場合はキャッシュを区別し、アカウント切り替え時のデータ残留も確認する。

[Query キー](https://tanstack.com/query/latest/docs/framework/vue/guides/query-keys) · [Vue のリアクティビティ](https://tanstack.com/query/latest/docs/framework/vue/reactivity) · [キャッシュの無効化](https://tanstack.com/query/latest/docs/framework/vue/guides/query-invalidation)

## 明示的な検索の実装案

確定条件ができるまで `enabled` を偽にする。初回確定またはキー変更では `useQuery` 側の取得だけを使い、同じキーを再検索するときだけ `refetch()` を呼ぶ。比較時は `staleTime: 0` とし、キャッシュ済みキーへの切り替えでも再取得する。ボタンは現在条件の取得中に無効化し、同じ検索操作の重複を防ぐ。

比較時は `retry: false`、`refetchOnMount: false`、`refetchOnWindowFocus: false`、`refetchOnReconnect: false` とする。キャッシュがなく確定条件が残った状態で画面が再マウントされる場合は、新規取得が起き得るため、詳細から戻る際の仕様とともに確認する。本番でリトライを設定する場合も、契約不一致は再試行の対象から外す。

## 採用前に決めることと確認すること

| 観点 | 採用判断に必要な確認 |
| --- | --- |
| 検索と再検索 | 未検索時は通信しない。条件変更時の初回取得と同じ条件での明示的な再検索を区別し、各操作で GET が1回だけ発生することを MSW で確認する。キャッシュがあるキーを再度検索する場合も含める。 |
| 自動再取得・再試行 | フォーカス復帰、再接続、画面再表示、リトライの既定挙動を確認する。PoC 比較時は自動再取得とリトライを抑え、AC1 の1回送信と、HTTP 500 の表示を再現する。 |
| キャッシュの寿命 | `staleTime` はデータを新鮮とみなす時間、`gcTime` は未使用になったキャッシュの保持時間。詳細画面から一覧へ何分後に戻っても復元すべきかを要件として整理し、設定を決める。アプリ再起動をまたぐ永続化は別判断。 |
| 競合とキャンセル | 現行 AC3 は同じキーで古い応答が最新結果を上書きしないことを求める。同一キーの要求は取得状況によって共有されるため、常に後発が別リクエストになる前提を置かない。要求が取り消された際の結果反映と、ネットワーク通信自体の中断は分けて確認する。後者は Query が渡す `AbortSignal` を生成クライアントの Fetch まで伝える必要がある。 |
| テスト | Vitest の結合テストごとに QueryClient を作成し、MSW で正常・空・500・契約不一致を再現する。Storybook の表示用部品は従来どおり固定値で確認する。Playwright で検索のリクエスト数と一覧表示を照合する。 |

[Query の既定値](https://tanstack.com/query/latest/docs/framework/vue/guides/important-defaults) · [Query のキャンセル](https://tanstack.com/query/latest/docs/framework/vue/guides/query-cancellation) · [在庫 PoC の受入基準](../08-poc/ht-inventory-poc.md#受入基準とテスト)

採用に進む場合は、変更範囲を Query の登録、在庫取得の composable、レスポンス Store を参照している画面とテストに絞る。API 契約、Orval の生成、Zod 検証、MSW モックは現行を再利用する。採用版と再取得方針が揃った段階で、計画書・Store 設計・API 境界の利用側・コンポーネント契約・アーキテクチャ図・単体と結合テストを更新する。AC1 の1回送信は Playwright と MSW で確認する。AC3 の UT-INV-01〜03 は QueryClient と取得 composable をつなぐケースに移し、前回データの保持、条件ごとの分離、同一キーの要求共有と取り消し後の結果を確認する。API 境界の単体テストは維持する。現行 AC3 の競合時の期待結果を変更する場合は、人間が確認してから受入基準を更新する。
