# Pinia の状態管理方針

## 画面制御とレスポンス保持

| 状態の置き場所 | 責務 | 例 |
| --- | --- | --- |
| 画面制御 Store | 画面間で共有または復元する UI 状態 | 検索条件の復元、開いていたパネル、一覧のスクロール位置、画面をまたぐ通知 |
| レスポンス Store | 業務単位で API の取得と結果を管理し、画面で再利用する | 検索条件とページごとの一覧、ID ごとの詳細、取得中・エラー・取得時刻 |
| コンポーネント内 | 表示中の画面だけで使う一時的な状態 | 復元が不要な入力途中の値、一時的なダイアログの開閉 |

検索実行時に画面から条件をレスポンス Store の action へ渡す。レスポンス Store はその条件で取得し、画面は保持されたデータから表示に必要な値を参照する。詳細から戻るときは画面制御 Store の条件・スクロール位置と、レスポンス Store の一覧を組み合わせて復元する。

検索キーには API の結果を変える条件、ページ、並び順を含める。同じキーで再取得が重なった場合は新しい要求の結果を優先する。入庫などの更新で在庫が変わった場合は、影響する一覧・詳細の再取得または無効化を行う。初回はメモリ保持を想定し、再起動後の復元が必要になった時点で永続化を検討する。

Store の action と保存ルールは Vitest で確認し、詳細から戻ったときの復元は Playwright の代表フローに含める。

[Pinia の Store 定義](https://pinia.vuejs.org/core-concepts/) · [Pinia の actions](https://pinia.vuejs.org/core-concepts/actions.html) · [Pinia のテスト](https://pinia.vuejs.org/cookbook/testing.html)

## 在庫 PoC の検索条件の正規化

商品コードの前後の空白を取り除く処理は共通関数に置く。検索画面は入力の確認と確定時にその関数を使い、空白のみなら取得を依頼しない。レスポンス Store は、取得 action と結果の参照の両方で同じ関数を使い、同じ正規化済みのキーを参照する。API 境界には正規化済みの条件を渡す。

## 取得に失敗した場合と同時取得

検索キーごとに `data`、`status`、`error`、`fetchedAt` を持つ案とする。取得失敗時は同じキーの最後の成功データと取得時刻を保持し、エラーを表示する。成功データがある場合は、その表示を維持したうえで再取得できるようにする。

同じキーでは最新の要求だけが成功・失敗を反映する。異なるキーの応答は各キーの領域に保存し、画面は現在選択中のキーだけを参照する。通信の中断を利用するかは API 導入時に決める。

## 導入時の確認

- 同じ検索条件の再取得、別の検索条件への切り替え、在庫更新後、詳細から戻った場合の保持ルールを具体化する。

現行の在庫 PoC は Pinia のレスポンス Store を採用する。TanStack Query を見送る理由と再検討条件は [TanStack Query の導入判断](ht-tanstack-query-pinia.md) を参照する。
