## must

### M1. 初回の範囲と対象外が書かれていない

- 場所：`ht-design.md:27`、`:31-36`、`:63-68`
- 問題：初回が「Java プラグインの疎通と Camera の撮影確認」であることが、要件の節にしか書かれていない。「決めること」(:34) では初回の範囲が未定のまま。一方、概要設計・詳細設計・テスト方針・API・Store の資料は、業務アプリ全体（入庫・在庫、Orval、Pinia、Storybook、Playwright）を前提にしている。このため、最初の PR の完了条件を決められない。
- 修正案：`ht-design.md` に「初回の範囲」と「初回の対象外」の節を追加する。
  - 範囲：プロジェクトの初期化、疎通確認用の画面 1 つ、独自プラグイン（Web 実装と Java 実装）、Camera の呼び出し、Android プロジェクトの生成。
  - 対象外：業務画面、Orval・Zod、業務用の Pinia Store、Storybook、Playwright、バーコード・OCR の認識、メーカー SDK。

  あわせて「決めること」の :34 を解決済みとして記録する。

### M2. 初回の実装に必要なバージョンと構成が決まっていない

- 場所：`ht-design.md:3`、`:47`
- 問題：CLAUDE.md では、Node.js・Vue・Capacitor のバージョン、パッケージマネージャー、対象プラットフォームを初期セットアップの方針で決めることになっている。ところが :47 では「次に決めること」のまま残っている。また Vite・Vue Router が「候補」とされている一方で、`ht-testing.md:9` と `:21` は Router の採用を前提にしている。
- 修正案：初回に採用するものを確定して記載する。
  - 決める項目：Node.js（メジャーバージョン）、パッケージマネージャー、Vue・Vite・TypeScript・Vuetify・Capacitor のメジャーバージョン、Android の minSdk / targetSdk、JDK、Android Studio の版、lint・型チェック・テスト・ビルドのコマンド。
  - Capacitor 8 が要求する Node・JDK・Android SDK の下限は、公式の移行ガイドで確認したうえで書く。レビュー時点では未確認。
  - Vuetify 4 のリリース状況と、Vite・Storybook との組み合わせも同様に確認が必要。
  - 未確定のものは「初回では入れない」と明記する。

### M3. 独自プラグインの受入基準が検証できる形になっていない

- 場所：`ht-design.md:24`、`:60`
- 問題：「共通 API を呼び出せる」「固定応答」「Java 側のログ」の具体的な中身が決まっていないため、合否を判定できない。
- 修正案：初回分のインターフェースを決めて記載する。
  - プラグイン名とメソッド名：例として `HtBridge.ping({ message: string }) => { value: string; platform: 'web' | 'android' }`。
  - Web 実装の固定応答の値。
  - Java 側のログタグ（例：`Log.d("HtBridge", ...)`）と、ログの確認方法（`adb logcat -s HtBridge`）。
  - Java 側で失敗した場合の扱い（`call.reject` の内容と、画面での表示）。

### M4. Camera の受入基準に、権限拒否・キャンセル・Web での挙動がない

- 場所：`ht-design.md:25`、`ht-testing.md:22`
- 問題：CLAUDE.md は、ネイティブ API について権限拒否と Web での挙動も確認するよう求めている。しかし今の基準は成功時の撮影だけ。「撮影結果がアプリに返る」の判定方法も決まっていない。
- 修正案：次のケースを受入基準に加える。
  - 撮影成功：`webPath` などで画像を画面に表示できる。
  - 撮影キャンセル：エラー表示を出さずに元の画面へ戻る。
  - カメラ権限の拒否：メッセージを表示し、再操作の方法を案内する。設定画面へ誘導するかどうかも決める。
  - Web での挙動：`@ionic/pwa-elements` を入れてブラウザで撮影できるようにするか、「Web では未対応のメッセージを出す」と決める。

  受け取る形式（`resultType`）と、確認した実機（機種・Android のバージョン）の記録欄も設ける。

## should

### S1. 読み取り画面の図は公式 Camera では実現できない

- 場所：`ht-layout-components.md:15`、`ht-screen-layout.drawio` 2 ページ目の `preview`（:148）と `mode`（:145）
- 問題：`@capacitor/camera` は端末のカメラアプリを起動して写真を受け取る仕組みで、アプリ内でのプレビュー表示や、プレビュー中の連続読み取りはできない。また HT では、内蔵スキャナーをメーカー SDK やインテント経由で使うのが一般的なので、読み取り画面の構成そのものが SDK の選定次第で変わる。
- 修正案：読み取り画面には「メーカー SDK の選定後に確定する（初回は対象外）」と注記する。初回の撮影確認は、疎通確認用画面から Camera を呼ぶだけと明記する。

### S2. 詳細から戻ったときの復元範囲が資料ごとに違う

- 場所：`ht-design.md:42`、`ht-layout-components.md:13`、`ht-store.md:11`、`ht-screen-layout.drawio` 1 ページ目 :80
- 問題：`ht-design.md` では復元範囲が「次に決めること」になっている。一方、ほかの 3 か所では「条件・結果・スクロール位置を復元する」と決まった扱いになっている。
- 修正案：決定事項とするなら、`ht-design.md:42` から削除する。未決にするなら、残りの 3 か所を「案」と表記する。

### S3. 取得に失敗したときの Store の扱いが Store の資料にない

- 場所：`ht-store.md:8`、`:13`、`ht-api.md:7`、`ht-testing.md:19`
- 問題：「失敗時に前回成功したデータを保持する」は API とテストの資料にしか書かれていない。Store の資料には次の点もない。
  - 前回のデータを検索キーごとに保持するのか。
  - 失敗時に、前回のデータとエラーを同時に表示するのか。
  - 別のキーで取得が競合したときの扱い（古い検索の応答が後から届いて上書きする問題）。
  - 古い要求が失敗したときに、新しい要求の成功状態を上書きしない条件。
- 修正案：`ht-store.md` に、キーごとの状態（`data`・`status`・`error`・`fetchedAt`）を書く。あわせて「画面が今表示しているキー以外の応答は捨てる」こと、`AbortController` を使うかどうか、エラーの種類（通信失敗・タイムアウト・HTTP エラー・契約不一致）ごとの state と表示を明記する。

### S4. API のエラーの分類と表示・再操作の対応がない

- 場所：`ht-api.md:7`、`ht-design.md:36`、`:46`
- 問題：エラーを 3 種類に区別するとは書かれているが、次の点が決まっていない。
  - タイムアウト、オフライン、認証切れ（401）の扱い。
  - エラーレスポンス本文も Zod で検証するか。
  - エラーの種類ごとに、どのメッセージを出し、どう再操作させるか。
- 修正案：エラーの種類を列挙し、それぞれについて画面の表示と再操作を表にする。業務画面が初回の対象外なら、この内容は後続の作業として明記するだけでもよい。

### S5. 想定外の項目を受け取ったときの期待値が決まっていない

- 場所：`ht-api.md:11`、`:17`
- 問題：導入時の確認項目に「想定外の項目」があるが、除去する（strip）、そのまま通す（passthrough）、エラーにする（strict）のどれを期待するかが書かれていない。
- 修正案：既定は strip とし、テストでは「仕様外のキーが除去されること」を期待値にする、と明記する。

### S6. 疎通確認のテストと記録の方法がない

- 場所：`ht-testing.md:11`、`:22`
- 問題：プラグインの呼び出しを Vitest で確認する項目と、Web 実装の固定応答を確認する項目がない。CLAUDE.md は新しい振る舞いにテストを付けることを求めている。また、ネイティブで確認した結果の記録形式もない。
- 修正案：次の 2 つを追加する。
  - Vitest：プラグインをモックして、画面のボタンから成功・失敗・キャンセルが表示に反映されることを確認する。Web 実装の固定応答の単体テストも行う。
  - 記録テンプレート：日付、端末またはエミュレーター（機種・Android のバージョン・API レベル）、ビルドの種類、手順、結果、ログの抜粋。

### S7. Store の名前が資料ごとに違う

- 場所：`ht-design.md:44`、`ht-store.md:8`、`ht-api.md:7`
- 問題：同じ Store が「API レスポンス取得・保持用 Store」「レスポンス Store」「データ Store」と 3 通りに呼ばれている。
- 修正案：「レスポンス Store」に統一する。

### S8. 作業を始める前提が整っていない

- 場所：作業ディレクトリ全体
- 問題：レビュー時点では git リポジトリではなく、GitHub の Issue もない。
- 修正案：初回の実装の前に、`git init` を行うか GitHub のリポジトリを作るかを決める。GitHub の準備前に進めるなら、ローカルの作業記録をどこに置くかも決める（例：`docs/records/`）。
