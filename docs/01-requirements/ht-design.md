# Android HT アプリの要件定義

Android ハンディターミナル向けの業務アプリを開発する。

## これまでに整理した要求

- 対象業務は入庫と在庫管理を想定する。
- 業務メニューから各業務画面へ進める。業務画面から関連業務へも進め、候補が多い場合は一覧から選ぶ。
- 業務画面では条件ごとのアコーディオンで検索条件を入力し、結果をカードで表示する。カードを選ぶと詳細情報を確認できる。
- 検索や読み取りの操作ボタンはフッターに置く。
- 各業務から共通の読み取り画面を開き、バーコードまたは OCR の結果を呼び出し元の入力項目に反映できる。

## 初回の範囲

Vue アプリ、Vuetify 4、Vue Router の初期化、疎通確認画面1つ、Android プロジェクトの生成、独自 Capacitor プラグインの Web・Java 実装、公式 Camera による撮影確認、Vitest のテストを含める。

## 初回の対象外

業務画面、業務用 MainLayout、業務用 Pinia Store、Orval・Zod、Storybook、Playwright、バーコード・OCR の認識、端末メーカー SDK 連携。利用するメーカー SDK は TBD。

在庫検索、API 生成、テスト基盤は [在庫管理 PoC](../08-poc/ht-inventory-poc.md) の別作業で確認する。

## ネイティブ疎通の受入基準

- 画面操作から Web 実装および Android の独自 Java プラグインを呼び出し、応答とログを確認できる。
- Android 実機で撮影し、画像が画面に表示される。撮影のキャンセル、権限拒否、その他の失敗、Web での案内を確認できる。

[受入ケースと確認手順](../07-system-test/README.md#初回のネイティブ受入確認)

## 決めること

- 入庫と在庫管理のどちらから設計するか。利用者、検索項目、カードと詳細に表示する項目、業務ごとの遷移先。
- カメラ確認に使う Android 実機と対象 HT。Android SDK とエミュレーターの準備はネイティブ検証の段階で扱う。
- 物理キー（トリガーキー・テンキー）の操作と対象画面サイズ。
- 業務上必要な性能、オフライン時の利用範囲、認証やデータ保持の要件。

## 要件の決定状況

| 決めること | 状況 | 現時点の内容 | 残っている判断 |
| --- | --- | --- | --- |
| 対象業務 | 決定済み | 入庫・在庫管理を想定する。 | 業務アプリとして先に仕上げる業務と利用者を決める。在庫検索は PoC の題材として決定済み。 |
| 入庫の業務ルール | 未決 | 入庫を対象とすることまで決定。 | 入庫対象の特定、数量・入力チェック、登録確定・取消、在庫反映のルール。 |
| 在庫管理の業務ルール | 方針あり | まず検索・一覧・詳細を想定。 | 本番の絞り込み条件、表示項目、更新操作を含めるか、業務上の受入基準。 |
| 読み取り | 方針あり | バーコード・OCR の結果を呼び出し元の入力に反映する。 | 対象コード、読み取り結果の確認方法、誤読時の操作、メーカー SDK の要否。 |
| 利用条件 | 未決 | Android HT 向け。 | 認証・権限、オフラインの要否、データ保持、性能、物理キー操作と表示要件。 |
| 初回 Android 疎通 | 決定済み | Web・Java の呼び出しと Android 実機での撮影確認。業務画面と認識処理は後続。 | 検証環境と実施結果の確定。 |

## 業務フローとシナリオの定義

業務フローは、誰が何を目的に始め、どの判断を経て完了するかを整理する。シナリオは、そのフローから条件を一つ選び、利用者の操作と観察できる結果を具体化する。要件を合意する時点で代表的な正常シナリオと、利用者の判断が変わる例外シナリオを定義する。基本設計で画面遷移と表示を、詳細設計で入力値・状態・応答を具体化する。

| 資料 | 記載項目 |
| --- | --- |
| 業務フロー | ID、利用者、目的、開始条件、主な手順と分岐、完了状態 |
| シナリオ | ID、業務フロー ID、前提、利用者の操作、観察できる期待結果、対応する受入基準 ID |
